# Blazor Benchmark

Одно и то же приложение «Мини-Магазин» — товары, заказы, оплаты, клиенты, дашборд, витрина
компонентов и страница диагностики — собрано на трёх библиотеках компонентов Blazor:

| Приложение | Библиотека | Тема | Лицензия |
|---|---|---|---|
| `src/Shop.Flare` | Flare.Blazor 0.45.0 | Material Design 2 | MIT |
| `src/Shop.MudBlazor` | MudBlazor 9.11.0 | Material | MIT |
| `src/Shop.Radzen` | Radzen.Blazor 12.1.4 | Material | MIT |

Страницы, данные, правила валидации и подписи общие и лежат в `src/Shop.Shared`; отличается
только UI-слой — так сравнение показывает разницу библиотек, а не разницу приложений.

## Бэкенда нет

`Shop.Shared` имитирует бэкенд прямо в браузере: детерминированный набор товаров, клиентов,
заказов и оплат плюс те же бизнес-правила, что были в API (остатки на складе, переходы статусов
заказа, лимит суммы оплаты). Изменения живут до перезагрузки страницы. Поэтому весь сайт —
статика, и он целиком помещается на GitHub Pages.

## Запуск

```bash
dotnet build BlazorBenchmark.slnx
```

Три приложения локально (5201 / 5202 / 5203):

```bash
powershell -File scripts/run-all.ps1 -Build
```

Весь сайт одним контейнером — лендинг и три приложения, как на Pages:

```bash
docker compose up -d --build
```

Открыть <http://localhost:8080>.

Собрать сайт локально в `artifacts/site` (та же раскладка, что публикует CI):

```bash
powershell -File scripts/publish-site.ps1 -BasePath /BlazorBenchmark
```

## Публикация

Workflow `.github/workflows/pages.yml` публикует лендинг в корень сайта, а приложения —
в `/flare/`, `/mudblazor/`, `/radzen/`. Перед первым запуском включить Pages:
**Settings → Pages → Source: GitHub Actions**.

Прямые ссылки внутрь приложений (`/flare/orders`) разбирает корневой `404.html`: GitHub Pages
отдаёт на неизвестный путь только его, а он переносит маршрут в строку запроса, и `index.html`
приложения возвращает адрес на место до старта Blazor.

## Что сравнивать

Страница **Диагностика** в каждом приложении собирает одинаковый набор показателей общим
скриптом `diagnostics.js`: тайминги загрузки и отрисовки (FP, FCP, LCP, готовность интерфейса),
длинные задачи, состав и вес ресурсов по группам (рантайм .NET, пакет библиотеки, шрифты),
размер DOM и число CSS-правил, JS-куча, параметры устройства. Отчёт копируется в буфер обмена
одной кнопкой — удобно складывать рядом три приложения.

Размеры публикаций: `powershell -File scripts/measure-sizes.ps1`.

## Контролируемый стенд компонентов

`Bench.*` сравнивает Flare, MudBlazor, Radzen, Blazorise (Bootstrap) и Fluent UI.
Внутри стенда ссылка **Buttons, inputs, toggles, selects and DataGrid** открывает `?mode=components`.
Он проверяет button, text input, number input, checkbox, switch, select и DataGrid;
прежние сценарии даты и времени доступны по обратной ссылке.

```powershell
./scripts/bench-compare-publish.ps1 -Output artifacts/components-fresh
node scripts/bench-compare-serve.mjs artifacts/components-fresh .claude/tests/components-fresh 16000 3 40 components
# Открыть URL Open из вывода; держать измеряемую вкладку видимой до завершения серии.
node scripts/bench-components-summary.mjs .claude/tests/components-fresh
node --test scripts/*.test.mjs
```

Каждому варианту/раунду нужен новый origin: повторное использование портов запрещено журналом.
Каталоги публикации и результатов тоже должны быть новыми. Сервер автоматически чередует порядок
библиотек и выполняет cold/warm документы. Это локальный сборщик результатов; на статическом хостинге
кнопка **Measure all components** работает без него и позволяет скачать JSON.

Для обычных контролов одинаковы 1/50 экземпляров, значения, 100 вариантов select и проверки callback.
Действие выполняется над первым контролом; нагрузка 50 измеряет его задержку в большой форме,
а не последовательный ввод во все 50 полей.
Измеряются первый mount, 8 remount, 8 неизменных parent rerender, первое и 8 повторных действий.
Наборы выполняются в одном порядке в одном документе: first означает первое действие данного
набора после предыдущих компонентов, а не отдельный холодный процесс для каждого типа.
У custom select отдельно измеряется открытие popup; у native select Blazorise это честное N/A,
а не нулевая задержка. Ввод заменяет полный текст через синтетические DOM-события, а не эмулирует IME.
Открытие custom select ждёт нужный отрисованный пункт; перед выбором отдельно завершается
анимация popup. Ожидание анимации не входит в задержку callback выбора.
Пункт custom select получает DOM click без дополнительной цепочки pointer/mousedown;
фокусируемые цели открытия получают фокус перед кликом. Это протокол commit, а не полный физический жест.

DataGrid отображает 100/1000 строк и 5 одинаковых колонок без виртуализации. Проверяется каждая
ячейка и порядок строк после общей сортировки, фильтрации, замены окна из 50 строк и обновления цены.
Это сравнение отображения одинаково подготовленных данных, **не нативных движков сортировки,
фильтрации, пагинации или редактирования**. Масштаб свыше 1000 строк в этой серии не оценивается.

Сводка хранит DOM completion, следующий кадр, pooled median/p95 и медианы отдельных документов;
8 действий внутри документа не выдаются за 8 независимых запусков. Пропущенный сценарий, неправильное
bound value, неверные ячейки или несовпадение SHA256 загруженных JS/CSS делают серию неполной.
Тайминги включают общий fixture, обновление снимка состояния и DOM-проверки; это задержка
сценария стенда, а не изолированное CPU-время библиотеки. Один раунд пригоден для QA, но не для рейтинга.
Material, Bootstrap и Fluent различаются дизайном: общая таблица результатов не означает паритет MD2.
FluentNumberInput использует IMask 7.6.1: точная npm-зависимость и MIT license включены в
`Bench.FluentUI/wwwroot/vendor`, чтобы CDN не влиял на результат и стенд работал автономно.
